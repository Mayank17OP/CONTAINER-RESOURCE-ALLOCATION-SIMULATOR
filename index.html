Scheduler comparison

              same load, three policies
            

            

              

              

                
                Each policy is run against the same workload and host. Weighted fair-share respects weight ratios, equal share ignores them, and strict priority serves the highest-weight container first — which starves low-weight workloads.

How the simulation actually computes an allocation

        

          Two independent mechanisms are applied on every time step. The CPU allocator answers
          “how much processing capacity does each container receive?”. The memory manager answers
          “is each container still inside its own hard boundary?”. They never share state.
        

        

          ei = min(di, qi)
          Σai ≤ C
          ai ≤ ei
          usage > limit → pressure
        

      


      


        

          
CPU allocation rule

          

            

              
Step 1 — eligible demand. A container cannot receive more than it
              wants, and never more than its cap:

              
ei = min(di, qi)

              
Step 2 — contention test. If Σeᵢ ≤ C every container is
              simply granted its eligible demand and the rest of the host sits idle.
              Otherwise the host is overcommitted and capacity is shared in proportion to
              the active weights.

              
Step 3 — progressive filling. Each pass hands every active container
              wᵢ / Σw × remaining, capped at what it still needs. A container that
              saturates its eligible demand drops out and its unused slice is redistributed on the
              next pass. The loop ends when capacity is exhausted or every container is satisfied.

              

                0 ≤ ai ≤ ei
                  and  
                Σai ≤ C
              

              
This is the same max-min fairness idea Linux cgroup v2 applies through
              cpu.weight and cpu.max.

            

          

        


        

          
Memory hard limits

          

            

              
A memory limit is a boundary, not a share. It is checked per
              container against that container's own counter, so one workload can never consume
              another's allowance.

              
    
                
  • usage ≥ 90% of limit → near limit
    • 
                
  • usage > limit → memory pressure
    • 
                
  • usage > 1.25 × limit → OOM (simulated)
    • 
              

              
An OOM here is a state change only. No process
              is signalled and no kernel setting is touched — the simulator reports what the
              kernel's OOM killer would have done.

              

                
                The simulator never starts real containers and never changes host settings.
                It is an accounting model, not a benchmark.

Abstract

          

            

              
Multiple containers share a finite pool of CPU and RAM on one host. A busy workload
              can slow down its neighbours, and a leaking one can exceed the memory it is permitted
              to use. This project builds an interactive simulator that makes those
              two effects visible and measurable.

              
The simulator models a host with configurable vCPU and RAM
              capacity, a set of containers each with CPU demand, a CPU cap, a relative weight and a
              memory hard limit, and then executes a repeatable simulation cycle: generate workload →
              apply CPU caps and weighted fair-share → check per-container memory limits → update the
              dashboard, metrics and event history.

            

          

        


        

          
Objectives

          

            

              
    
                
  • Model host capacity — configurable vCPU and RAM for the shared machine.
    • 
                
  • Set container limits — demand, CPU cap, weight and memory limit per workload.
    • 
                
  • Simulate contention — weighted, equal and strict-priority sharing with throttling.
    • 
                
  • Monitor isolation — memory pressure/OOM alerts with a full event history.
    • 
              

            

          

        


        

          
System architecture

          

            

              

                
INPUT

Memory manager

                
Independent per-container counters checked against each hard limit.

Metrics, charts, throttling ratios, alerts and the event log.

Scope & limitations

          

            

              
What it demonstrates:

              
    
                
  • Host CPU and RAM configuration
    • 
                
  • Per-container CPU caps and relative weights
    • 
                
  • Weighted CPU sharing during contention
    • 
                
  • Memory hard limits and pressure alerts
    • 
                
  • Separate resource counters and event history
    • 
              

              
Current limitations:

              
    
                
  • Does not start real Docker containers
    • 
                
  • Does not change Linux kernel settings
    • 
                
  • CPU model is simplified weighted sharing
    • 
                
  • OOM is represented as a simulated state
    • 
                
  • Results are not physical host benchmarks
    • 
              

            

          

        


        

          
Conclusion & future work

          

            

              
Conclusion. CPU and memory isolation need separate but coordinated
              controls. Weighted sharing distributes CPU under contention, CPU caps bound each
              container's allocation, memory hard limits detect overuse, and separate counters
              demonstrate accounting isolation.

              
Future work:

              
    
                
  • Integrate Docker Engine and Linux cgroup v2 for real enforcement
    • 
                
  • Add time-series export and downloadable run logs
    • 
                
  • Compare additional CPU scheduling policies
    • 
                
  • Add memory reservation, swap and OOM policy options
    •
